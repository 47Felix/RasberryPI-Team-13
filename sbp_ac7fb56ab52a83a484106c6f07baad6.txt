Ziel: Der Prototyp ist aktuell ein Demo mit hardgecodeten Posts
aus data/posts.json. Baue daraus eine echte, funktionierende App:

1. SCHEMA & MIGRATION
   Entwirf ein Postgres-Schema für Supabase mit mindestens:
   - authors (id, name, handle, avatar_url)
   - categories (id, name)
   - posts (id, author_id, category_id, content, created_at,
     perspective enum: 'pro'/'contra'/neutral falls sinnvoll)
   - likes (post_id, user_session_id, created_at)
   Schreibe das SQL als Migration-Datei
   (supabase/migrations/0001_init.sql) inkl. sinnvoller Indizes
   und Row Level Security (RLS): anon darf lesen und Posts/Likes
   einfügen, aber nichts löschen/updaten außer eigene Likes.
   Gib mir das SQL am Ende NICHT nur in einer Datei, sondern auch
   nochmal im Chat aus, damit ich es im Supabase SQL Editor
   ausführen kann.

2. ANBINDUNG
   Nutze supabase-py (Client via SUPABASE_URL + SUPABASE_ANON_KEY
   aus Umgebungsvariablen/.env, NIE hardcoden). Ersetze die
   JSON-basierten Reads/Writes in app.py und ranking.py durch
   DB-Zugriffe. Lege eine .env.example an (ohne echte Werte) als
   Vorlage, die echte .env bleibt lokal und ungetrackt.

3. NEUE POSTS ERSTELLEN
   Baue ein Formular/Endpoint, mit dem ein Nutzer einen eigenen
   Post erstellen kann (Text + Kategorie-Auswahl aus categories).
   Automatische Kategorisierungs-Vorschläge: nutze weiterhin
   TF-IDF-Ähnlichkeit zu bestehenden Posts je Kategorie, um dem
   Nutzer eine Kategorie vorzuschlagen (er kann sie überschreiben).

4. LIKES
   Like/Unlike-Button pro Post (Toggle), Like-Zähler sichtbar,
   ohne Login über eine simple Session-ID (Cookie) gebunden.

5. ALGORITHMUS AUF ECHTEN DATEN
   standard_feed und diversity_aware_feed in ranking.py müssen
   jetzt aus der DB rechnen statt aus posts.json. Berücksichtige
   Likes optional als Signal (z.B. beliebte Posts leicht bevorzugen,
   ohne dass das die Diversity-Logik aushebelt).

6. TESTS
   Aktualisiere tests/test_ranking.py so, dass er gegen eine
   Test-DB oder gemockte Supabase-Antworten läuft (kein Netzwerk-
   Zugriff in CI). Alle Tests müssen grün sein, bevor du committest.
